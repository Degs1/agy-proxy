# Requirements Document

## Introduction

Antigravity Gateway adalah satu aplikasi Next.js App Router dan TypeScript yang berjalan di Vercel serta terhubung langsung ke MongoDB Atlas. MVP menyediakan dashboard khusus admin, pengelolaan project dan API key, penyimpanan credential provider terenkripsi, endpoint REST yang kompatibel dengan cakupan OpenAI Chat Completions yang ditetapkan di bawah, SSE streaming, pembatasan request dan concurrency terdistribusi, serta monitoring. Gemini API resmi adalah provider aktif pertama.

`docs/PRD.md` tetap menjadi acuan tujuan produk. Kontrak yang dapat diuji untuk MVP ditetapkan dalam dokumen ini. Sebelum implementasi, Bayu dan Reza SHALL mencatat dan menyelesaikan perbedaan antara kedua dokumen. Verifikasi E2E SHALL menggunakan format flow YAML dan runner yang berlaku di workspace.

| Milestone | Urutan dan hasil | Penanggung jawab | Estimasi kasar |
| --- | --- | --- | --- |
| M1  Foundation dan keamanan | Aplikasi, koneksi Atlas, autentikasi admin, project, API key, credential terenkripsi | Bayu; review Reza | 12 minggu |
| M2  Gateway dan streaming | Adapter Gemini, kontrak REST, rate limit, concurrency, SSE | Bayu; review Reza | 12 minggu |
| M3  Monitoring dan dashboard | Telemetri operasional, alur admin, desain dan implementasi UI | Nala dan Fira; API Bayu; review Reza | 1 minggu |
| M4  Verifikasi dan deployment | Flow YAML E2E, review keamanan, konfigurasi Vercel, pemeriksaan produksi | Reza; perbaikan Bayu dan Fira | 35 hari |

Estimasi bergantung pada akses Atlas, kuota Gemini, dan hasil verifikasi streaming serta pembatasan lintas instance di lingkungan target.

## Assumptions

- MVP menggunakan Gemini API resmi. Antigravity OAuth dan inference belum diaktifkan tanpa dokumentasi serta izin resmi yang terverifikasi.
- Fork 9Router bukan dependensi MVP. Penggunaannya sebagai referensi memerlukan pemeriksaan lisensi dan kepatuhan.
- Pengembangan lokal menggunakan MongoDB Atlas secara langsung tanpa Docker Compose.
- Atlas yang digunakan SHALL mendukung transaksi multi-dokumen. Seluruh instance SHALL menggunakan database yang sama untuk keputusan admission dan lease.
- Setiap project memiliki daftar alias model yang diizinkan. Alias awal `gemini-default` dipetakan oleh admin ke satu model Gemini resmi dan **satu credential Gemini aktif milik project yang sama**. Pengikatan credential bersifat eksplisit per alias; tidak ada pemilihan otomatis berdasarkan urutan atau prioritas credential. Nama model Gemini aktual adalah konfigurasi, sehingga perubahan katalog provider tidak mengubah kontrak publik.
- Batas awal setiap project adalah **60 request per menit UTC** dan **5 request aktif**. Admin dapat mengubah keduanya menjadi bilangan bulat positif; nilai baru berlaku untuk admission berikutnya.

### Requirement 1

**Judul:** Foundation aplikasi dan penyimpanan data  
**Milestone/Prioritas:** M1 / Must  
**Penanggung jawab:** Bayu; review Reza  
**Dependensi:** Akses MongoDB Atlas yang mendukung transaksi dan konfigurasi proyek Vercel.

**User Story:** As a pengelola sistem, I want satu aplikasi yang dapat dijalankan di Vercel dan terhubung langsung ke MongoDB Atlas, so that gateway dan dashboard dapat dioperasikan tanpa VPS atau service router terpisah.

#### Acceptance Criteria

1. WHEN aplikasi dijalankan secara lokal atau di Vercel, THEN aplikasi SHALL menggunakan Next.js App Router dan TypeScript serta mengakses MongoDB Atlas melalui konfigurasi lingkungan.
2. IF konfigurasi wajib atau koneksi database tidak tersedia, THEN aplikasi SHALL menolak operasi yang bergantung padanya dan menghasilkan kesalahan yang dapat ditelusuri tanpa membocorkan rahasia.
3. WHEN skema data dan indeks disiapkan, THEN aplikasi SHALL mendukung admin, sesi admin, penghitung percobaan login, project, API key, credential provider, catatan penggunaan, penghitung rate, keputusan admission berdasarkan identitas request, dan lease concurrency yang digunakan bersama oleh seluruh instance. Indeks unik SHALL mencegah lebih dari satu keputusan admission untuk kombinasi project, identitas API key, dan identitas request yang sama.

### Requirement 2

**Judul:** Akses dashboard khusus admin  
**Milestone/Prioritas:** M1 / Must  
**Penanggung jawab:** Bayu untuk autentikasi dan otorisasi; Fira untuk integrasi UI; review Reza  
**Dependensi:** Requirement 1.

**User Story:** As a admin, I want dashboard yang hanya dapat diakses oleh admin terautentikasi, so that konfigurasi gateway dan data operasional terlindungi.

#### Acceptance Criteria

1. WHEN sistem pertama kali disiapkan, THEN operator SHALL membuat admin awal melalui perintah bootstrap yang dijalankan dengan akses lingkungan deployment dan kredensial Atlas; tidak ada endpoint registrasi publik. Perintah SHALL menerima email admin dan kata sandi dari input rahasia, menyimpan hash kata sandi Argon2id, serta gagal jika admin awal sudah ada. Bootstrap SHALL membuat dokumen penjaga ber-ID tetap dan admin awal dalam satu transaksi Atlas; indeks unik pada ID penjaga SHALL memastikan hanya satu dari bootstrap yang berjalan bersamaan dapat berhasil. WHEN admin masuk menggunakan email dan kata sandi yang benar, THEN server SHALL membuat token sesi acak, menyimpan hanya hash token beserta ID admin, waktu kedaluwarsa, waktu aktivitas terakhir, dan status pencabutan di Atlas, lalu mengirim token dalam cookie `__Host-admin_session` dengan `HttpOnly`, `Secure`, `SameSite=Strict`, dan `Path=/`. Login yang salah SHALL tidak membuat sesi. Setiap akses halaman atau API administrasi SHALL memeriksa token, masa berlaku, status pencabutan, dan hak admin di sisi server.
2. IF pengguna tidak memiliki sesi sah atau hak admin, THEN aplikasi SHALL menolak API administrasi dengan HTTP `401` atau `403` sesuai penyebab dan SHALL tidak menampilkan data dashboard. Sesi SHALL berakhir paling lambat 12 jam sejak dibuat atau setelah 30 menit tanpa aktivitas; aktivitas yang sah memperbarui waktu aktivitas terakhir di Atlas. Setiap operasi administrasi yang mengubah state, termasuk logout, SHALL mensyaratkan `Origin` yang sama dengan origin aplikasi dan token CSRF khusus sesi yang dikirim dalam header `X-CSRF-Token`; token SHALL diverifikasi di sisi server. Login SHALL mensyaratkan `Origin` yang sama. Permintaan yang gagal pemeriksaan CSRF SHALL mendapat HTTP `403` tanpa perubahan state.
3. WHEN admin keluar atau sesi dicabut, THEN server SHALL menandai sesi sebagai dicabut di Atlas, menghapus cookie pada browser, dan menolak penggunaan token tersebut pada seluruh instance mulai dari request administrasi berikutnya. Sesi yang melewati batas waktu absolut atau tidak aktif SHALL ditolak dengan cara yang sama. Pencabutan SHALL diperiksa terhadap Atlas pada setiap request administrasi; cache lokal tidak boleh memperpanjang akses.
4. WHEN endpoint login menerima percobaan, THEN server SHALL membatasi kegagalan menjadi paling banyak **5 per email yang dinormalisasi** dan **20 per alamat IP sumber tepercaya** dalam jendela berjalan 15 menit, menggunakan state bersama di Atlas sehingga batas berlaku lintas instance. Email yang tidak terdaftar SHALL tetap dihitung. IF salah satu batas tercapai, THEN percobaan berikutnya SHALL mendapat HTTP `429` dengan `Retry-After` dalam detik sampai batas tersebut berakhir; server SHALL tidak memeriksa kata sandi atau membuat sesi. Login gagal sebelum batas tercapai SHALL memberi respons generik yang sama untuk email terdaftar dan tidak terdaftar. Identitas sumber SHALL berasal dari metadata koneksi atau proxy deployment yang dipercaya, bukan header klien yang dapat dipalsukan. IF sumber tidak dapat dipastikan atau state pembatasan tidak tersedia, THEN login SHALL gagal aman dengan HTTP `503`. Keberhasilan login SHALL menghapus hitungan kegagalan email tersebut, tetapi tidak menghapus hitungan sumber.

### Requirement 3

**Judul:** Pengelolaan project, API key, dan credential provider  
**Milestone/Prioritas:** M1 / Must  
**Penanggung jawab:** Bayu untuk data dan API; Fira untuk UI; review Reza  
**Dependensi:** Requirement 1 dan Requirement 2.

**User Story:** As a admin, I want membuat dan mengelola project, API key, serta credential provider, so that akses gateway dapat dikendalikan per project.

#### Acceptance Criteria

1. WHEN admin membuat, melihat daftar, memperbarui, atau menonaktifkan project dan konfigurasi model serta batasnya, THEN aplikasi SHALL menyimpan perubahan dan menampilkan status terbaru. Setiap alias model SHALL menyimpan ID credential yang terikat, ID project pemiliknya, nama model Gemini aktual, dan status aktif atau nonaktif. Pembuatan atau perubahan alias SHALL ditolak jika credential yang dipilih tidak aktif, bukan milik project tersebut, atau bukan credential Gemini. Project atau alias yang dinonaktifkan SHALL tetap tersimpan untuk administrasi, tetapi tidak menerima request gateway baru.
2. WHEN API key project dibuat, THEN aplikasi SHALL menghasilkan sedikitnya 256 bit acak menggunakan generator bilangan acak kriptografis, menampilkan nilai rahasianya hanya pada saat pembuatan, dan menyimpan hanya hash kriptografis satu arah beserta metadata yang diperlukan untuk mengenali key. Nilai hash atau representasi tersimpan lainnya SHALL tidak dapat digunakan sebagai bearer key untuk autentikasi gateway.
3. IF API key tidak valid, telah dicabut, atau tidak berhak memakai project terkait, THEN gateway SHALL menolak request dengan HTTP `401` sebelum memanggil provider. IF key sah tetapi project pemiliknya nonaktif, THEN gateway SHALL mengembalikan HTTP `403` dengan kode `project_disabled`. IF project aktif tetapi alias miliknya nonaktif, THEN gateway SHALL mengembalikan HTTP `403` dengan kode `model_disabled`. Alias yang tidak terdaftar mengikuti Requirement 5, AC 3. Penolakan tersebut SHALL memakai bentuk error Requirement 5, AC 3 dan SHALL terjadi sebelum admission atau panggilan provider. Untuk request baru maupun retry, gateway SHALL memeriksa autentikasi key, lalu status project dan alias, sebelum mencari keputusan admission lama. Karena itu, key yang dicabut SHALL mendapat `401` dan project atau alias yang dinonaktifkan SHALL mendapat `403` meskipun UUID request memiliki keputusan `rejected` yang masih tersimpan; keputusan tersebut tidak dihapus atau diubah.
4. WHEN credential provider disimpan, THEN aplikasi SHALL mengenkripsinya menggunakan authenticated encryption dan menyimpan ciphertext beserta identitas versi kunci. Kunci enkripsi SHALL berasal dari secret lingkungan di luar database dan SHALL tidak muncul dalam respons, log, atau dashboard. Penyimpanan credential baru SHALL gagal apabila kunci aktif tidak tersedia.
5. WHEN kunci enkripsi dirotasi, THEN aplikasi SHALL mengenkripsi credential baru dengan versi kunci aktif, tetap dapat membaca credential lama menggunakan versi kunci sebelumnya, dan menyediakan proses migrasi serta verifikasi sebelum kunci lama dinonaktifkan. IF versi kunci yang diperlukan hilang, salah, atau gagal memverifikasi ciphertext, THEN pembacaan credential dan request provider yang bergantung padanya SHALL gagal secara aman tanpa memakai plaintext pengganti, tanpa meneruskan request ke provider, dan tanpa menampilkan nilai rahasia.
6. WHEN admin mencabut API key atau credential, atau menonaktifkan project atau alias, THEN perubahan SHALL berlaku pada request gateway yang admission-nya commit setelah perubahan admin commit di seluruh instance. Perubahan admin SHALL ditulis dalam transaksi yang menulis penjaga limiter project yang sama dengan transaksi admission. Gateway SHALL memverifikasi ulang status API key, project, alias, pengikatan credential, dan status credential dari Atlas di dalam transaksi admission setelah menulis penjaga tersebut; pemeriksaan sebelum transaksi tidak menentukan apakah request baru diterima. Request dianggap diterima tepat saat transaksi admission commit. Konflik tulis SHALL dicoba kembali terhadap state terbaru, sehingga request yang admission-nya commit sebelum perubahan admin merupakan operasi yang sudah berjalan. Gateway SHALL tidak menggunakan cache lokal untuk memperpanjang akses. IF credential yang terikat pada alias dicabut, tidak tersedia, atau tidak dapat didekripsi, THEN request baru untuk alias tersebut SHALL gagal dengan HTTP `503` dan kode `provider_unavailable` sebelum panggilan provider; gateway SHALL tidak beralih ke credential lain. Admin SHALL mengikat alias ke credential aktif lain secara eksplisit untuk memulihkan layanan.

### Requirement 4

**Judul:** Kontrak adapter provider dan Gemini API resmi  
**Milestone/Prioritas:** M2 / Must  
**Penanggung jawab:** Bayu; review Reza  
**Dependensi:** Requirement 3.

**User Story:** As a pengelola gateway, I want provider diakses melalui adapter modular dengan Gemini API resmi sebagai implementasi pertama, so that provider lain dapat ditambahkan tanpa mengubah kontrak gateway.

#### Acceptance Criteria

1. WHEN gateway memilih provider aktif, THEN aplikasi SHALL memanggilnya melalui kontrak adapter yang memisahkan validasi, pengiriman request, normalisasi respons, streaming, dan pemetaan kesalahan.
2. WHEN request memakai alias model dengan credential Gemini aktif yang terikat pada alias tersebut dan dimiliki project yang sama, THEN adapter SHALL memanggil API Gemini resmi memakai credential itu dan mengembalikan hasil melalui kontrak gateway. Gateway SHALL tidak memilih credential lain meskipun project memiliki beberapa credential Gemini. Adapter SHALL memetakan setiap pesan `system` pada awalan percakapan menjadi bagian instruksi sistem dalam urutan aslinya, setiap `user` menjadi pesan Gemini berperan `user`, dan setiap `assistant` menjadi pesan Gemini berperan `model`. Adapter SHALL mempertahankan urutan pesan dan teks setiap bagian tanpa menghapus, menyatukan, atau mengubah peran pesan. Urutan yang boleh diteruskan ditetapkan pada Requirement 5, AC 1; urutan lain SHALL ditolak sebelum panggilan provider.
3. IF provider gagal atau menolak request, THEN adapter SHALL menghasilkan HTTP `502` dengan kode `provider_error` tanpa mengungkap credential. IF provider tidak dapat dihubungi atau credential terikat tidak dapat dipakai, THEN adapter SHALL menghasilkan HTTP `503` dengan kode `provider_unavailable`. Keluaran kosong, keluaran diblokir, dan alasan selesai yang tidak dapat dipetakan SHALL mengikuti Requirement 5, AC 5.
4. WHEN adapter provider baru ditambahkan, THEN kontrak REST publik SHALL tetap dapat digunakan tanpa perubahan khusus provider pada klien.

### Requirement 5

**Judul:** Endpoint REST kompatibel OpenAI  
**Milestone/Prioritas:** M2 / Must  
**Penanggung jawab:** Bayu; review Reza  
**Dependensi:** Requirement 3 dan Requirement 4.

**User Story:** As a pengembang aplikasi klien, I want mengirim request melalui API yang kompatibel dengan OpenAI, so that integrasi klien dapat menggunakan gateway dengan perubahan minimal.

#### Acceptance Criteria

1. WHEN klien mengirim `POST /v1/chat/completions` dengan header `Authorization: Bearer <API_KEY_PROJECT>`, `Content-Type: application/json`, dan `Idempotency-Key: <UUID>`, THEN gateway SHALL menerima **hanya** field tingkat atas `model`, `messages`, `stream`, `temperature`, dan `max_tokens`. Ukuran body JSON SHALL paling banyak **1 MiB (1.048.576 byte)**; gateway SHALL menghentikan pembacaan saat batas terlampaui dan mengembalikan HTTP `413` dengan kode `payload_too_large` serta `param: null`. `model` SHALL berupa alias yang diizinkan untuk project tersebut. `messages` SHALL berupa array berisi **1 sampai 64 item**; setiap item SHALL berisi **hanya** `role` dan `content`, dengan `role` berupa `system`, `user`, atau `assistant` dan `content` berupa string tidak kosong sepanjang paling banyak **32 KiB (32.768 byte) dalam UTF-8**. Jumlah pesan di luar batas SHALL menghasilkan HTTP `400`, kode `invalid_request`, dan `param: "messages"`; konten di luar batas SHALL menghasilkan HTTP `400`, kode `invalid_request`, dan `param` yang menunjuk `messages[i].content`. Urutan yang didukung SHALL terdiri dari nol atau lebih pesan `system` di awal, diikuti pesan `user` pertama, lalu pesan `assistant` dan `user` yang bergantian; pesan terakhir SHALL berperan `user`. Beberapa pesan `system` awal SHALL dipertahankan sebagai bagian instruksi terpisah dalam urutan aslinya. Pesan `system` setelah percakapan dimulai, pesan `user` atau `assistant` berurutan dengan peran sama, percakapan yang dimulai atau berakhir dengan `assistant`, dan percakapan yang hanya berisi `system` SHALL ditolak dengan HTTP `400`, kode `invalid_request`, dan `param` yang menunjuk `messages[i].role` pada pesan pertama yang melanggar aturan, atau `messages` jika tidak ada pesan `user`. Field opsional yang didukung adalah `stream` berupa boolean, `temperature` berupa angka dari **0 sampai 2, termasuk 0 dan 2**, dan `max_tokens` berupa bilangan bulat dari **1 sampai 8192**. Nilai `temperature` di bawah 0 atau di atas 2 SHALL ditolak dengan HTTP `400`, kode `invalid_request`, dan `param: "temperature"`; nilai `max_tokens` di luar batas SHALL ditolak dengan HTTP `400`, kode `invalid_request`, dan `param: "max_tokens"`. Jika `stream` tidak ada, nilainya dianggap `false`. `Idempotency-Key` SHALL berupa UUID yang dibuat klien untuk satu percobaan logis dan dipakai kembali tanpa perubahan ketika klien mengulang percobaan tersebut. Versi API publik MVP adalah `/v1`; endpoint dan versi lain tidak dijanjikan.
2. WHEN request nonstream berhasil dan provider menghasilkan teks tidak kosong dengan alasan selesai yang dapat dipetakan, THEN gateway SHALL mengembalikan HTTP `200` dengan objek yang memuat `id`, `object: "chat.completion"`, `created` sebagai Unix timestamp dalam detik, `model` berisi alias yang diminta, dan `choices` berisi tepat satu item dengan `index: 0`, `message: { "role": "assistant", "content": "<teks>" }`, serta `finish_reason` berupa `stop` atau `length`. `usage` SHALL berisi `prompt_tokens`, `completion_tokens`, dan `total_tokens` jika angka terukur tersedia; jika tidak tersedia, `usage` SHALL bernilai `null`.
3. IF API key tidak ada, salah, atau dicabut, THEN gateway SHALL mengembalikan HTTP `401`. IF alias model tidak terdaftar untuk project pemilik key, THEN gateway SHALL mengembalikan HTTP `404` dengan kode `model_not_found` tanpa mengungkap model milik project lain. Status project dan alias nonaktif mengikuti Requirement 3, AC 3. IF payload, nilai field, struktur JSON, atau `Idempotency-Key` tidak valid, THEN gateway SHALL mengembalikan HTTP `400` dengan kode `invalid_request`. Seluruh kesalahan sebelum respons dimulai SHALL berupa JSON `{ "error": { "message": "<pesan aman>", "type": "<jenis>", "param": "<nama field atau null>", "code": "<kode>" } }`; respons retry terminal boleh menambahkan metadata hasil yang ditetapkan Requirement 6, AC 4. Tidak satu pun kondisi validasi ini memanggil provider.
4. IF request memuat field tingkat atas atau field dalam item `messages` di luar daftar yang diterima pada AC 1, THEN gateway SHALL menolaknya dan SHALL tidak mengabaikannya diam-diam. Field kemampuan OpenAI yang dikenal tetapi di luar cakupan MVP, termasuk `tools`, `tool_choice`, `functions`, `function_call`, `response_format`, `logprobs`, `stream_options`, `n`, dan field multimodal seperti `image_url`, SHALL menghasilkan HTTP `400` dengan kode `unsupported_feature` dan `param` yang menunjuk field tersebut; `n` juga ditolak ketika bernilai `1` karena field itu tidak diterima dalam kontrak MVP. Field lain yang tidak dikenal SHALL menghasilkan HTTP `400` dengan kode `invalid_request` dan `param` yang menunjuk field tersebut. `content` yang bukan string ditolak sebagai `unsupported_feature` jika memuat input multimodal, dan sebagai `invalid_request` untuk bentuk lain yang salah. Cakupan ini hanya berlaku untuk Chat Completions berbasis teks; endpoint embeddings, images, audio, dan Responses API berada di luar MVP.
5. WHEN provider mengembalikan hasil, THEN gateway SHALL mempertahankan identitas `id` yang sama sepanjang satu respons dan mengisi `usage` hanya dari angka yang benar-benar tersedia. Alasan selesai Gemini `STOP` SHALL dipetakan ke `stop`, dan `MAX_TOKENS` ke `length`. IF provider menyatakan keluaran diblokir, termasuk alasan keselamatan atau kebijakan maupun blokir pada prompt, THEN gateway SHALL menghasilkan HTTP `502` dengan kode `provider_output_blocked`; teks parsial tidak boleh dilaporkan sebagai keberhasilan. IF respons selesai tanpa teks, THEN gateway SHALL menghasilkan HTTP `502` dengan kode `provider_empty_response`. IF alasan selesai lain tidak dapat dipetakan, THEN gateway SHALL menghasilkan HTTP `502` dengan kode `provider_error`. Kegagalan tersebut dan kegagalan pada Requirement 4, AC 3 SHALL menggunakan bentuk error pada AC 3.

### Requirement 6

**Judul:** Rate limiting dan concurrency terdistribusi  
**Milestone/Prioritas:** M2 / Must  
**Penanggung jawab:** Bayu; review Reza  
**Dependensi:** Requirement 1, Requirement 3, dan Requirement 5.

**User Story:** As a admin, I want batas request dan request aktif berlaku lintas instance Vercel, so that satu project tidak melampaui kapasitas yang ditetapkan.

#### Acceptance Criteria

1. WHEN request telah lolos autentikasi dan validasi payload, tetapi sebelum provider dipanggil, THEN gateway SHALL mengambil keputusan admission melalui **satu transaksi MongoDB Atlas**. Transaksi SHALL lebih dahulu menulis dokumen penjaga limiter milik project dengan operasi yang menghasilkan waktu server Atlas; waktu tersebut SHALL menjadi satu-satunya acuan untuk awal jendela menit UTC, masa berlaku lease, perpanjangan, dan penentuan lease kedaluwarsa. Dalam transaksi yang sama, gateway SHALL membaca ulang status API key, project, alias, pengikatan credential, dan status credential dari Atlas serta menolak request yang tidak lagi berhak sebelum mencatat keputusan admission. Transaksi SHALL memeriksa penghitung rate pada jendela tetap satu menit UTC yang dimulai pada detik `00`, menghitung lease project dengan `expires_at` **lebih besar** dari waktu server tersebut, lalu menyimpan kenaikan penghitung rate, lease unik dengan masa berlaku 45 detik, dan catatan keputusan admission untuk kombinasi `(project_id, api_key_id, Idempotency-Key)`. Seluruh perubahan SHALL commit bersama atau seluruhnya batal; commit admission adalah titik request dianggap diterima. Penulisan penjaga yang sama pada perubahan administrasi terkait project, admission, perpanjangan, pelepasan, dan pemrosesan lease kedaluwarsa SHALL membuat operasi bersamaan pada project tersebut mengalami konflik tulis dan dihitung ulang terhadap state terbaru; konflik transaksi yang dapat diulang SHALL dicoba kembali. Batas awal adalah 60 request yang diterima per project per jendela dan 5 request aktif. IF salah satu batas penuh, THEN transaksi SHALL mencatat penolakan sebagai keputusan terminal berstatus `rejected`, tanpa menaikkan kuota atau membuat lease, selama batas pencatatan penolakan pada AC 4 belum tercapai. Request yang diterima tetap menghitung kuota rate meskipun kemudian gagal atau dibatalkan.
2. IF batas rate terlampaui, THEN gateway SHALL menolak request sebelum provider dipanggil dengan HTTP `429`, kode `rate_limit_exceeded`, dan `Retry-After` dalam detik sampai awal jendela berikutnya. IF seluruh slot concurrency terpakai, THEN gateway SHALL menolak dengan HTTP `429`, kode `concurrency_limit_exceeded`, dan `Retry-After: 1`. Keduanya SHALL menggunakan bentuk error Requirement 5, AC 3. Jika keduanya penuh, `rate_limit_exceeded` SHALL dipilih secara konsisten. Selama API key tetap sah serta project dan alias tetap aktif, pengulangan dengan kombinasi `(project_id, api_key_id, Idempotency-Key)` dan payload yang sama SHALL mengembalikan HTTP `429` serta kode penolakan semula selama catatan keputusan masih disimpan, dengan `outcome` terminal sesuai AC 4. Pemeriksaan autentikasi dan status konfigurasi pada Requirement 3, AC 3 SHALL mendahului pencarian keputusan lama. Pada pengulangan penolakan `rate_limit_exceeded`, `Retry-After` SHALL dihitung ulang sampai akhir jendela penolakan yang tercatat dan SHALL dihilangkan setelah jendela itu berakhir; pengulangan penolakan `concurrency_limit_exceeded` SHALL tetap memakai `Retry-After: 1`.
3. WHEN slot concurrency diambil, THEN gateway SHALL membuat lease unik dengan masa berlaku 45 detik menurut waktu server Atlas pada transaksi admission. Selama request masih aktif, termasuk stream yang panjang, lease SHALL diperpanjang sekurangnya setiap 15 detik melalui transaksi yang menulis penjaga project, memperoleh waktu server Atlas, dan hanya memperbarui lease dengan identitas yang sama jika `expires_at` masih **lebih besar** dari waktu tersebut. Perpanjangan yang commit SHALL mengatur `expires_at` menjadi 45 detik setelah waktu transaksi itu. Pada batas tepat `expires_at`, lease SHALL dianggap kedaluwarsa dan tidak dapat diperpanjang. Penyelesaian, kegagalan, pembatalan klien, dan timeout SHALL memicu transaksi pelepasan yang menulis penjaga project dan mengubah keputusan request menjadi terminal. IF proses berhenti mendadak, THEN transaksi admission atau retry berikutnya SHALL menandai lease kedaluwarsa sebagai terminal dan mengabaikannya dalam hitungan slot, sehingga kapasitas pulih paling lambat 45 detik sejak perpanjangan terakhir tanpa bergantung pada jadwal penghapusan TTL database. IF perpanjangan lease gagal, kedaluwarsa, atau hasilnya tidak dapat dipastikan, THEN gateway SHALL segera menghentikan pengiriman dan pemrosesan keluaran provider, membatalkan aliran upstream melalui adapter, dan mengakhiri respons sesuai Requirement 7, AC 3 dan Requirement 7, AC 5. Keluaran yang datang terlambat SHALL dibuang tanpa diproses, diteruskan, atau mengubah keputusan terminal; pekerjaan tersebut SHALL tidak lagi memakai slot atau kapasitas pemrosesan gateway setelah lease tidak sah.
4. WHEN sedikitnya dua instance aplikasi berbagi Atlas dan mengirim request bersamaan untuk project yang sama, THEN jumlah admission pada menit UTC yang sama SHALL tidak melebihi batas rate dan jumlah lease aktif yang belum kedaluwarsa SHALL tidak melebihi batas concurrency. Catatan keputusan admission SHALL memiliki indeks unik pada `(project_id, api_key_id, Idempotency-Key)` dan disimpan sedikitnya 24 jam sejak keputusan menjadi terminal; `api_key_id` adalah identitas internal key yang telah terautentikasi, bukan nilai bearer key. Untuk membatasi penulisan akibat UUID penolakan baru, paling banyak **1.000 keputusan `rejected` baru per project per hari UTC** SHALL dicatat; penghitung bersama SHALL diperiksa dan dinaikkan secara atomik dalam transaksi keputusan. Setelah batas tersebut tercapai, gateway SHALL tetap mengembalikan `429` dan kode penolakan yang berlaku tanpa menyimpan keputusan baru atau membuat lease; respons SHALL tidak memuat `outcome`. Retry UUID yang tidak tercatat tersebut SHALL dinilai ulang terhadap batas yang berlaku saat retry, sehingga idempotensi dan pemulihan hasil terminal tidak dijanjikan untuk penolakan yang melewati batas pencatatan. Keputusan yang sudah tercatat SHALL tetap tersedia sedikitnya 24 jam dan dipakai pada retry sebelum penghitung pencatatan diperiksa. Key lain dalam project yang sama SHALL tidak dapat memperoleh keputusan atau `outcome` milik key pertama melalui UUID yang sama. Sidik request SHALL dihitung dari payload JSON yang telah lolos validasi dan hanya mencakup nilai `model` berupa nama alias yang diminta, array `messages` beserta urutan dan nilai `role` serta `content` setiap item, nilai `stream`, serta keberadaan dan nilai `temperature` dan `max_tokens`. Urutan field objek JSON SHALL diabaikan; `stream` yang dihilangkan SHALL dinormalisasi menjadi `false`; angka SHALL dibandingkan menurut nilai numeriknya sehingga, misalnya, `1` dan `1.0` setara; `temperature` atau `max_tokens` yang dihilangkan SHALL tetap berbeda dari nilai yang dikirim secara eksplisit. Teks SHALL dibandingkan sebagai nilai string JSON setelah penguraian, tanpa normalisasi Unicode tambahan. Sidik request SHALL memakai nama alias yang diminta, bukan model Gemini atau credential hasil konfigurasi alias; perubahan konfigurasi alias setelah keputusan tersimpan SHALL tidak mengubah sidik atau memicu panggilan provider ulang pada retry. Setelah pemeriksaan autentikasi dan status konfigurasi pada Requirement 3, AC 3 berhasil, pengulangan dengan kombinasi identitas yang sama dan sidik request berbeda SHALL menghasilkan HTTP `409` dengan kode `idempotency_conflict`. Pengulangan dengan identitas dan sidik request yang sama SHALL memakai keputusan yang sudah tersimpan, tanpa menaikkan rate, membuat lease baru, atau memanggil provider lagi: keputusan `running` dengan lease sah menghasilkan HTTP `409` berkode `request_in_progress`; keputusan terminal selain `rejected` menghasilkan HTTP `409` berkode `request_already_processed`; keputusan `rejected` mengikuti HTTP `429` dan kode penolakan semula pada AC 2. Respons retry terminal SHALL menambahkan objek `outcome` berisi `status` (`succeeded`, `failed`, `cancelled`, `lease_expired`, atau `rejected`), `original_http_status`, `original_error_code` atau `null`, dan `completed_at`. Untuk `rejected`, `original_http_status` SHALL bernilai `429`, `original_error_code` SHALL berisi kode penolakan semula, dan `completed_at` SHALL mencatat waktu keputusan penolakan commit. `succeeded` SHALL berarti provider menyelesaikan request dengan hasil sah; untuk stream, chunk akhir dan `[DONE]` telah disiapkan untuk dikirim. Status ini tidak menjamin klien menerima seluruh byte respons. Respons terminal SHALL tidak menyimpan atau mengembalikan isi pesan maupun teks hasil. Sebelum memilih respons retry, gateway SHALL menjalankan transaksi yang menulis penjaga project dan, jika lease `running` telah kedaluwarsa, mengubah keputusan itu menjadi terminal dengan hasil `lease_expired`. Kegagalan proses yang terdeteksi SHALL mengubah keputusan menjadi terminal dengan hasil `failed` saat lease dilepas. Dengan demikian, retry setelah proses mati atau lease kedaluwarsa SHALL mendapat `request_already_processed` beserta status terminalnya, bukan `request_in_progress` tanpa batas waktu. Klien SHALL memakai key yang sama untuk mengetahui hasil terminal setelah koneksi putus selama masa penyimpanan; key baru berarti percobaan logis baru dan dapat memanggil provider lagi. Setelah catatan dihapus, gateway tidak menjanjikan pemulihan status key tersebut. Pengujian SHALL mencakup tabrakan pada slot terakhir, retry, pembatalan stream, proses yang dihentikan mendadak, dan pemulihan sesudah lease kedaluwarsa.
5. IF Atlas atau operasi state pembatasan tidak tersedia, atau hasil commit transaksi tidak diketahui karena koneksi terputus, THEN gateway SHALL **tidak memanggil provider** sampai keputusan admission dipastikan. Gateway SHALL terlebih dahulu membaca catatan keputusan dengan read concern `majority` dan, jika perlu, mengulang transaksi memakai kombinasi `(project_id, api_key_id, Idempotency-Key)` yang sama. IF keputusan tetap tidak dapat dipastikan sebelum batas waktu admission, THEN gateway SHALL mengembalikan HTTP `503` dengan kode `limiter_unavailable`; transaksi yang ternyata telah commit tetap menghitung satu kuota dan satu lease yang akan dilepas atau kedaluwarsa. IF transaksi dipastikan batal atau belum commit, THEN retry boleh membuat tepat satu keputusan baru. Kegagalan sebelum commit SHALL tidak mengurangi kuota atau mengambil slot; kegagalan setelah commit tetapi sebelum panggilan provider SHALL tidak membatalkan kuota yang sudah diterima. Gateway SHALL tidak meneruskan request tanpa keputusan admission yang terkonfirmasi.

### Requirement 7

**Judul:** SSE streaming dan pembatalan request  
**Milestone/Prioritas:** M2 / Must  
**Penanggung jawab:** Bayu; review Reza  
**Dependensi:** Requirement 4, Requirement 5, dan Requirement 6.

**User Story:** As a pengembang aplikasi klien, I want menerima keluaran model secara bertahap melalui SSE, so that pengguna dapat melihat respons sebelum generasi selesai.

#### Acceptance Criteria

1. WHEN request valid memakai `"stream": true` dan provider mulai menghasilkan teks yang sah, THEN gateway SHALL mengembalikan HTTP `200` dengan `Content-Type: text/event-stream` dan mengirim baris `data: <JSON>\n\n`. Setiap chunk normal SHALL memuat `id` yang sama, `object: "chat.completion.chunk"`, `created`, `model`, dan `choices` berisi satu item dengan `index: 0`, `delta`, serta `finish_reason`. Chunk awal SHALL memuat `delta: { "role": "assistant" }`; chunk teks SHALL memuat `delta: { "content": "<teks>" }`; chunk akhir SHALL memuat `delta: {}` dan `finish_reason: "stop"` atau `"length"`. Chunk akhir hanya boleh dikirim setelah provider dipastikan selesai dengan alasan yang dapat dipetakan. Setelah chunk akhir, gateway SHALL mengirim tepat satu `data: [DONE]\n\n` lalu menutup stream. Contoh urutan:

   ```text
   data: {"id":"chatcmpl-123","object":"chat.completion.chunk","created":1793664000,"model":"gemini-default","choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

   data: {"id":"chatcmpl-123","object":"chat.completion.chunk","created":1793664000,"model":"gemini-default","choices":[{"index":0,"delta":{"content":"Halo"},"finish_reason":null}]}

   data: {"id":"chatcmpl-123","object":"chat.completion.chunk","created":1793664000,"model":"gemini-default","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

   data: [DONE]

   ```

2. WHEN provider menghasilkan bagian teks, THEN gateway SHALL meneruskannya sebagai chunk tanpa menunggu seluruh generasi selesai. Gateway SHALL menunda pembukaan respons SSE sampai teks pertama tersedia, sehingga kegagalan, blokir, keluaran kosong, atau timeout sebelum teks pertama dapat dikembalikan sebagai HTTP error JSON. IF blokir, keluaran kosong, atau alasan selesai yang tidak dapat dipetakan diketahui setelah stream dimulai, THEN gateway SHALL mengirim event error sesuai AC 5, tanpa chunk akhir yang menandakan keberhasilan, diikuti tepat satu `[DONE]`.
3. IF klien membatalkan koneksi, timeout request tercapai, atau lease tidak dapat diperpanjang, THEN gateway SHALL segera membatalkan aliran upstream melalui adapter, berhenti membaca atau memproses keluarannya, dan melepaskan slot concurrency melalui mekanisme Requirement 6, AC 3 jika lease masih sah. Keluaran provider yang tiba setelah pembatalan SHALL dibuang tanpa dikirim ke klien atau mengubah keputusan terminal. Batas waktu request nonstream adalah 120 detik; batas waktu stream adalah 10 menit. Runtime deployment SHALL dikonfigurasi agar durasi fungsi dan koneksi stream mendukung 10 menit tersebut beserta waktu untuk mengirim error dan melepas lease; lingkungan yang memutus stream lebih awal tidak memenuhi syarat. Timeout SHALL memakai kode `gateway_timeout` dan HTTP `504` sebelum respons dimulai atau event error menurut AC 5 setelah stream dimulai. Kegagalan perpanjangan lease SHALL memakai kode `limiter_unavailable` dan HTTP `503` sebelum respons dimulai atau event error menurut AC 5 setelah stream dimulai. Pembatalan oleh klien tidak menghasilkan chunk atau `[DONE]` tambahan karena koneksi telah tertutup.
4. IF kesalahan terjadi sebelum header SSE atau chunk pertama dikirim, THEN gateway SHALL mengembalikan HTTP error JSON sesuai Requirement 5, AC 3 dan tidak memulai stream. Contoh kegagalan provider sebelum stream dimulai:

   ```http
   HTTP/1.1 502 Bad Gateway
   Content-Type: application/json

   {"error":{"message":"Provider gagal memproses request.","type":"provider_error","param":null,"code":"provider_error"}}
   ```

5. IF kesalahan terjadi setelah stream dimulai, THEN gateway SHALL mengirim satu event `data: {"error":...}\n\n` dengan bentuk error Requirement 5, AC 3, diikuti tepat satu `data: [DONE]\n\n`, lalu menutup koneksi dan melepaskan slot. Event error ini adalah ekstensi gateway untuk kesalahan setelah HTTP `200`; klien SHALL memperlakukannya sebagai kegagalan, termasuk ketika chunk teks sudah diterima. Blokir SHALL memakai `provider_output_blocked`, keluaran kosong SHALL memakai `provider_empty_response`, alasan selesai yang tidak dapat dipetakan SHALL memakai `provider_error`, timeout SHALL memakai `gateway_timeout`, dan kegagalan lease SHALL memakai `limiter_unavailable`. Contoh:

   ```text
   data: {"error":{"message":"Provider gagal memproses request.","type":"provider_error","param":null,"code":"provider_error"}}

   data: [DONE]

   ```

### Requirement 8

**Judul:** Monitoring dan jejak penggunaan  
**Milestone/Prioritas:** M3 / Must  
**Penanggung jawab:** Bayu untuk pencatatan dan API; Fira untuk penyajian; review Reza  
**Dependensi:** Requirement 5 dan Requirement 7.

**User Story:** As a admin, I want melihat penggunaan dan kegagalan gateway per project dan provider, so that masalah operasional dapat ditemukan dan ditindaklanjuti.

#### Acceptance Criteria

1. WHEN request gateway terautentikasi berakhir atau gagal, THEN aplikasi SHALL mencatat waktu mulai, durasi, hasil, kode kesalahan bila ada, dan penggunaan token terukur bila tersedia. Catatan SHALL memuat ID project; alias model dan provider SHALL bernilai `null` bila belum dapat ditentukan, misalnya karena payload tidak valid atau alias tidak terdaftar. WHEN request ditolak sebelum API key terautentikasi, THEN aplikasi SHALL mencoba membuat catatan penolakan pra-autentikasi yang memuat waktu mulai, durasi, status HTTP, dan kode kesalahan; ID project, alias model, provider, dan penggunaan token SHALL bernilai `null`. Pencatatan pra-autentikasi SHALL dibatasi paling banyak **1.000 catatan per menit UTC** secara bersama lintas instance dan catatan tersebut SHALL dihapus paling lambat **7 hari** setelah dibuat. Penolakan yang melampaui batas pencatatan tidak menghasilkan catatan individual. Kegagalan menulis catatan operasional atau tercapainya batas pencatatan SHALL tidak menunda atau mengubah respons gateway yang sudah dapat ditentukan; kegagalan tersebut SHALL dapat ditelusuri melalui sinyal operasional terbatas volume tanpa mencatat rahasia atau isi pesan. IF Atlas tidak tersedia sehingga bearer key tidak dapat diverifikasi, THEN gateway SHALL mengembalikan HTTP `503` tanpa memanggil provider; penolakan yang dapat ditentukan tanpa akses Atlas, seperti header autentikasi yang tidak ada, SHALL tetap mengembalikan `401` meskipun catatannya tidak dapat ditulis.
2. WHEN admin membuka monitoring, THEN dashboard SHALL menampilkan ringkasan dan rincian per project serta provider yang tersedia, serta jumlah penolakan pra-autentikasi secara terpisah tanpa mengatribusikannya ke project atau provider.
3. IF data penggunaan dari provider tidak tersedia, THEN aplikasi SHALL menandainya sebagai tidak tersedia dan SHALL tidak menampilkan angka perkiraan sebagai angka terukur.
4. WHEN data dicatat atau ditampilkan, THEN aplikasi SHALL tidak mencatat API key, credential, isi pesan request, atau isi respons. Ketentuan ini berlaku juga untuk catatan penolakan pra-autentikasi, log aplikasi, dan tampilan dashboard.
